# 一、這份規範是什麼

定義一份規格書該有哪些章節、每章該寫什麼、不該寫什麼。

寫規格書前先讀這份。寫完後對照本文件的「交付檢查表」確認。

# 二、讀者與視角

規格書的讀者是三方。撰寫時必須讓三方各自找得到自己要的內容。

| 讀者      | 想知道                 | 主要讀哪幾章         |
| ------- | ------------------- | -------------- |
| 營運      | 這個功能能做什麼、不能做什麼      | 1、2、3、4、6、8、10 |
| UIUX 前端 | 畫面有什麼、怎麼互動、各種狀態怎麼呈現 | 4、5、6、7、8、9、11 |
| 後端      | 要提供什麼資料、有什麼規則       | 3、5、6、11、14    |
| QA      | 怎麼驗這個功能對不對          | 9、12、13        |

# 四、各章說明

## 文件控制表

放在標題下方。固定六列。

| 欄位      | 寫什麼           |
| ------- | ------------- |
| 文件性質    | 這是規格書、範例，還是規範 |
| 與現有文件關係 | 取代什麼、不取代什麼    |
| 本版目的    | 這一版要解決什麼問題    |
| 適用範圍    | 涵蓋哪些頁面或功能     |
| 不在本版範圍  | 明確排除的項目       |
| 上游依據    | 這份文件依據哪份上游文件  |

**「不在本版範圍」必填。** 這是防止範圍蔓延最有效的一欄。

## 目錄

三欄：章節、內容、主要讀者。

標出主要讀者，讓三方知道自己該讀哪幾章。

## 1. 這頁是什麼

寫什麼：

* 這個功能的用途

* 使用者在這裡做哪幾件事（條列）

* 這頁是唯讀還是可操作

注意：寫「使用者做什麼」，不寫「系統做什麼」。

## 2. 這頁不做什麼

兩欄表：不做的事、由誰負責。

只寫**會被誤以為在這裡做**的事。不窮舉所有不相關的功能。

## 3. 名詞說明

寫什麼：

* 三方會用到但認知可能不同的詞

* 系統內部物件的定義

* 容易混淆的欄位

**兩個名字相近、層級不同的欄位，必須在這章切開，並舉一個實例。**

例：「全域可用性」與「發布狀態」都叫狀態，但層級不同、來源不同、不可互相推導。

## 4. 畫面內容

寫什麼：

* 由上而下的區塊清單

* 每個區塊有什麼內容

* 表頭結構（如有多層表頭）

* 摘要數字的計算方式

注意：只寫「有什麼」，不寫「長什麼樣」。顏色、間距、字級不寫在規格書。

## 5. 欄位說明

表格逐欄列出：欄位名稱、內容、**無資料時顯示什麼**。

**「無資料時顯示什麼」必填。** 這是最常漏掉、也最常出問題的一格。

欄位下方補充規則，例如：哪些值不可顯示為 0、哪些 ID 只在詳情顯示。

## 6. 狀態說明

每一組狀態各一張表：值、顯示文字、意思。

規則：

* 同時列出**代碼**與**顯示文字**。代碼給後端看，顯示文字給營運看。

* 不同層級的狀態必須分開列表，不可合併成一張。

* 表格下方寫狀態之間的規則，例如什麼情況會自動改變、什麼情況不會。

## 7. 查詢、排序與分頁

寫什麼：

* 每個篩選條件的欄位名稱、型態、說明

* 查詢的觸發時機（即時或按鈕）

* 預設排序、可排序欄位

* 每頁筆數

規劃中但尚未實作的功能要標明，不與現況混寫。

## 8. 操作與跳轉

表格列出：點擊位置、前往哪裡、**帶入什麼參數**。

參數必填。沒有寫參數的跳轉，實作與驗收都會出錯。

## 9. 頁面狀態

至少涵蓋五種：

| 狀態   | 說明           |
| ---- | ------------ |
| 載入中  | 資料尚未回來       |
| 查無資料 | 查詢成功但沒有結果    |
| 載入失敗 | 查詢失敗         |
| 局部失敗 | 部分資料取不到，其他正常 |
| 無權限  | 使用者不能看這個頁面   |

**「查無資料」與「載入失敗」必須分開。** 兩者的使用者處置方式完全不同。

## 10～12. User Story

三章分別從三個角度描述同一個功能。詳見第五節。

## 13. 驗收標準

表格四欄：ID、主題、驗收敘述。

敘述使用 Given / When / Then 一行寫完。

每條驗收都要能被實際執行。寫不出具體操作步驟的條目不放進來。

## 14. 這頁需要的資料

給後端的資料需求。分成幾個能力區塊，每塊寫：輸入、輸出、規則。

**寫「需要什麼資料」，不寫 API 路徑、欄位名稱與 schema。**

正式介面在後端規格定義，不在功能規格書鎖死。

## 15. 待確認事項

分兩類：

| 類別    | 說明          |
| ----- | ----------- |
| 待產品決策 | 內部可以決定，等排時間 |
| 待外部輸入 | 要等其他團隊或外部系統 |

每項寫：編號、問題、影響範圍（或等待對象）。

處理原則見第八節。

## 16. 版本沿革

表格三欄：版本、日期、內容。

後續變更以最新版為基準建立，保留全部沿革，不覆蓋舊紀錄。

## 17. 交付檢查表

表格三欄：檢查面、完成條件、確認欄。

檢查面對應本文件的重點章節。完成條件必須是可以回答「是」或「否」的敘述。

# 五、User Story 撰寫規則

## 三個視角

| 章節 | 視角     | 問的問題   | 主要讀者       |
| -- | ------ | ------ | ---------- |
| 10 | 使用者    | 我要做什麼  | 營運         |
| 11 | 開發人員   | 我要做對什麼 | UIUX 前端、後端 |
| 12 | QA 驗證者 | 我要驗什麼  | QA         |

同一條規則可以在三章各出現一次。角度不同，不算重複。

## 格式

每一則使用一張表格：

```markdown
| **US-U01 標題** |
| :--- |
| 身為（角色），我要（目的）。 |
| **GIVEN** 前提條件。 |
| **WHEN** 觸發動作。 |
| **THEN** 預期結果。 |
```

沒有前提條件時可省略 GIVEN，其餘不可省略。

## 規則

* 一則只講一件事。講兩件事就拆成兩則。

* **GIVEN 要有具體數字或具體狀態。** 不寫「某些情況下」。

* **THEN 要可觀察。** 不寫「正確顯示」「正常運作」，要寫看到什麼。

* 每章建議 8～12 則。少於 6 則通常代表描述不完整。

# 六、編號規則

| 編號       | 用途              | 範例     |
| -------- | --------------- | ------ |
| `US-U##` | 使用者 User Story  | US-U01 |
| `US-D##` | 開發人員 User Story | US-D01 |
| `US-Q##` | QA User Story   | US-Q01 |
| `AC-##`  | 驗收標準            | AC-01  |
| `Q-##`   | 待確認事項           | Q-01   |

規則：

* 編號一旦發布就不重用、不重排。

* 移除的項目保留編號，內容改為「已移除，見 vX.X」。

* 新增項目接續最大號，不插號。

# 七、寫作規則

1. 一句話講一件事。不用逗號串三個子句。

2. 能用表格就不用段落。

3. 不寫「值得注意的是」「需要特別說明」「基本上」「原則上」。

4. 不寫形容詞。「完整的查詢功能」改成直接列出有哪些查詢條件。

5. 規則用「會／不會／必須／不可」，不用「建議」「盡量」「應該」。

# 八、待確認事項的處理原則

1. **查得到的先查，查不到才標。** 現有文件、原型或程式裡找得到答案的，不列入待確認。

2. **不填推測答案。** 沒有決策的地方留白並標明，不寫看起來合理的內容。

3. **分清楚待決策與待外部輸入。** 前者可以排時間解決，後者只能等。

4. **決議後更新，不刪除。** 更新狀態與決議內容，保留原始問題與編號。

一份好的規格書，待確認事項是**找出來的真問題**，不是填不滿的空格。找出十個真問題比填滿十個格子有價值。

# 九、版本管理

* 原始檔為 Markdown，存放於版本控制。

* 需要 Word 版本時由 Markdown 轉出，不反向編輯 Word。

* 轉檔指令：

```bash
pandoc -f markdown -t docx SPEC.md -o SPEC.docx
```

* 每次改版更新「版本沿革」，並同步檢查 User Story、驗收標準與待確認事項是否需要一併調整。
